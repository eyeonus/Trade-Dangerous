## Purpose

This slice extended the completed first safe slice from fixed station-to-station one-hop planning into bounded endpoint expansion.

The supported planning shape is now:

```text
endpoint text
  -> resolved endpoint
  -> candidate station set
  -> one-hop station-pair matrix
  -> best valid one-hop route
```

The planner can now accept systems as endpoints and expand them into eligible stations.

## Implemented Behaviour

### Endpoint Resolution

The planner now uses endpoint resolution rather than station-only resolution.

Resolved endpoints may represent:

```text
- fixed station endpoint
- system endpoint requiring station expansion
```

For scoped station input:

```text
System/Station
```

the station is resolved within the named system.

Scoped station lookup does not fall back to broad global station matching.

Bare endpoint resolution now supports exact system-or-station candidates.

This preserves an exact-first resolver shape suitable for later fuzzy matching.

---

### System Endpoint Expansion

System endpoints expand to eligible stations in the resolved system.

Expansion is bounded to the selected system only.

This is not broad galaxy search.

For a fixed station endpoint, the station remains a one-station tuple after filter validation.

For a system endpoint, eligible stations are fetched from the database and returned as the candidate source or destination set.

---

### Station Filters

Station-level filters are applied during system expansion where practical.

The SQLAlchemy-side station expansion predicates now cover:

```text
- system_id
- market availability
- pad size
- planetary state
- no-planet
- black-market state
- max ls distance
- fleet-carrier state
- settlement state
```

Fleet-carrier and settlement filtering are derived from `Station.type_id`.

The local and pushed `data_gateway.py` state includes the required station-type imports and type-id mappings.

---

### Filter Semantics

The accepted-set semantics remain in force for Y/N/? filters:

```text
Y    = known yes only
N    = known no only
?    = unknown only
Y?   = yes or unknown
N?   = no or unknown
YN   = yes or no, excluding unknown
YN?  = no filter
```

Pad-size filtering remains membership-based, not rank compatibility:

```text
S    = small only
M    = medium only
L    = large only
?    = unknown only
SM   = small or medium
ML   = medium or large
M?   = medium or unknown
ML?  = medium, large, or unknown
SML  = no filter
SML? = no filter
```

Invalid pad-size combinations still include:

```text
SL
SL?
```

---

### Station-Pair Matrix Evaluation

The planner now evaluates a one-hop matrix of candidate station pairs:

```text
for each source station:
  for each destination station:
    evaluate concrete station pair
```

For each non-self pair it performs:

```text
1. reachability check
2. market candidate query
3. cargo optimisation
4. practical score calculation
5. best-pair selection
```

Expected pair-level failures are skipped while evaluating the matrix.

The best valid pair is selected by practical score, with raw profit as tie-breaker.

---

### Self-Pair Handling

The planner now enforces the durable hop invariant:

```text
source station != destination station
```

This is done after station identity is known:

```text
source_station.station_id == destination_station.station_id
```

Self-pairs are skipped cheaply inside the matrix loop.

No raw endpoint-text rejection is performed.

This is intentional because future fuzzy matching may allow identical input text to resolve to different concrete stations.

Example future-safe case:

```text
--from "shin/jam" --to "shin/jam"
```

could theoretically resolve to two different stations, so raw text cannot be treated as identity.

---

### Market Candidate Query

The candidate query remains database-side and bounded to one concrete station pair.

It filters for:

```text
- source station id
- destination station id
- matching item id
- positive source supply price
- positive source supply units
- positive destination demand price
- positive destination demand units
- minimum gain per ton
- maximum gain per ton, where supplied
- minimum supply, where supplied
- minimum demand, where supplied
- age cutoff, where supplied
- affordability of at least one unit
```

Affordability pruning remains SQL-side:

```text
source_item.supply_price <= available_credits
```

This was deliberately retained because pruning unaffordable rows before cargo optimisation avoids unnecessary Python workload.

---

### Cargo Optimisation

The first-slice cargo optimiser is still used.

The implementation continues to enforce:

```text
- cargo capacity
- available credits after insurance reserve
- per-item cargo limit
- source supply
- destination demand as hard cap
- positive profit subject to gain filters
- exact total cost/profit arithmetic
```

No greedy-only replacement was introduced.

## Failure Behaviour

Aggregate failure handling remains intentionally simple for this slice.

The planner distinguishes:

```text
- no reachable station pair
- no reachable source station with usable selling data
- no reachable destination station with usable buying data
- no profitable trades across reachable station pairs
- profitable trades exist but no cargo can be afforded
```

Self-pair-only cases fall through normal aggregate failure handling.

No special spoon-fed error is emitted for users entering the exact same station twice.

This is acceptable for this slice.

## Performance Notes

The second slice remains bounded by endpoint systems.

It does not perform galaxy-wide station search.

The key performance principle preserved in this slice is:

```text
prune as early as correctness allows
```

Current pruning points include:

```text
- station filters during system expansion
- market quote role filters in SQL
- min supply / min demand in SQL
- age cutoff in SQL
- gain-per-ton in SQL
- affordability of at least one unit in SQL
- self-pair skip before reachability, market query, or cargo optimisation
```

A future multi-hop implementation must reassess diagnostic aggregation and station-pair evaluation cost before carrying the one-hop strategy directly into route-frontier expansion.

This note has already been identified as important for later documentation.

Known tradeoff: station-pair candidate queries prune unaffordable commodities in SQL.
If a pair has profitable commodities but all exceed available credits, the aggregate
failure may classify the pair as having no profitable candidates rather than no
affordable cargo. This is intentional on the hot path to avoid extra diagnostic
joins across large pair/frontier evaluations.
