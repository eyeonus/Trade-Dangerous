Data Scale note:

There are ~800K rows in Station
There are ~19M rows in StationItem

Candidate query should stay aggressively selective, not load known-dead rows into planner space

Candidates must be pruned as early as possible, ideally in SQL. Even if error granularity or some other feature could benefit from dead rows, reducing the selected rows must take priority.

Every “small” per-row check becomes expensive when multiplied by millions.

Default posture:
- trust established invariants;
- avoid speculative edge-case probes;
- push filtering into SQLAlchemy/DB-side predicates;
- avoid Python-side validation except as a safety net after already-narrowed result sets;
- do not add extra classification work unless it changes a real user-facing outcome or prevents an observed failure.


Multi-hop diagnostic granularity note:

Second Slice uses lightweight aggregate failure tracking across the bounded
one-hop station-pair matrix. This is cheap because every pair is already being
evaluated.

Before extending from one-hop to multi-hop route expansion, reassess whether
this diagnostic granularity should continue by default. Rich rejection-state
tracking across a combinatorial route frontier may increase complexity, memory
churn, and pruning burden.

Likely policy:
- keep detailed aggregate errors for bounded one-hop evaluation;
- use coarse failure counters/reasons for multi-hop by default;
- reserve richer telemetry for explicit diagnostics/debug mode if needed.
